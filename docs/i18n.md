One invariant across the whole migration: **string extraction should preserve current `en_us` output exactly.** Copy-editing can happen afterward, so failures during this work mean structural regressions rather than ambiguous wording changes.

### 1. Establish the `src/i18n` boundary and locale contract

**Deliverables**
- Add:
  ```text
  src/i18n/
    index.ts
    types.ts
    en_us/
      index.ts
  ```
- Define one `LocaleStrings` contract in `types.ts`.
- `en_us/index.ts` assembles the English sections and `satisfies LocaleStrings`.
- `i18n/index.ts` exports the active catalog, hardcoded to `en_us` for now.
- Keep `src/i18n` dependency-light. Ideally locale files import only other `i18n` files, not `domain`, `ui`, `app`, etc.
- Extend the architecture checker so `i18n` cannot acquire dependencies back into application layers.

**Avoid**
- No locale setting/config/UI yet.
- No dynamic imports or runtime translation library.
- No JSON catalogs; TypeScript functions are useful for interpolation/plurals and give compile-time checking.
- Do not create opaque translation IDs such as `STRING_183`.
- Do not make `i18n` import `domain` types merely for convenience.

**Regression traps**
- Margarita's architecture checker treats imports as dependency edges, including type imports. A `domain → i18n → domain` arrangement can therefore introduce a real architecture-cycle failure.
- A loose `Record<string, string>` contract will make missing translations invisible.
- Do not let `i18n/index.ts` become a dumping ground; it should just select/assemble the locale.

**Current source:** the existing locale-shaped interfaces currently depend on domain types in `src/domain/greeting-strings-en_us.ts:1-25` and `src/domain/throbber-strings-en_us.ts:1-72`. The cycle/import gate lives in `scripts/check-architecture.ts`, particularly its layer/policy and cycle logic.

### 9. Add guardrails so literals do not immediately drift back into feature code

Do this after the migration, not before it.

**Deliverables**
- Add an architecture rule: production `src/i18n/**` may depend on other `i18n` files but not `app`, `domain`, `ui`, `adapter`, `config`, etc.
- Ensure every locale object `satisfies LocaleStrings`, so adding a field to English establishes the required shape for future locales.
- Add focused formatter tests for plural/interpolation-heavy strings.
- Keep existing UI/controller tests asserting literal rendered English output.
- Document the rule succinctly: **semantic/machine strings stay with code; human-authored user-facing prose belongs in i18n.**

**Avoid**
- Do not create a naive lint rule that bans every string literal outside `i18n`; Margarita legitimately contains protocol strings, keys, filenames, separators, regexes, MIME types and command syntax.
- Do not change tests to assert:
  ```ts
  expect(output).toBe(strings.foo)
  ```
  everywhere. That only proves production and test imported the same constant.
- Don't require every punctuation mark or layout fragment to live in i18n.

**Regression traps**
- A test suite that imports the same catalog as production can no longer detect accidental copy changes.
- An overly broad literal scanner will produce enough false positives that it gets ignored.
- Future locale files must not reintroduce cross-layer dependencies.

**Current source:** `scripts/check-architecture.ts` already centralizes layer rules and cycle detection; `package.json` already puts `check:architecture` inside `verify`, so this is the correct existing enforcement point rather than adding an unrelated second architecture system.

This order gives you three useful checkpoints: **1–3 establish the mechanism**, **4–8 remove essentially all real user-facing prose from feature code**, and **9 prevents the tree from drifting back.**
